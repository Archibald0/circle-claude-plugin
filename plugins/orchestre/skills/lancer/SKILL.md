# Lancer un plan

Tu pilotes l'exécution de `$ARGUMENTS`. Tu restes léger : tu ne lis ni les fichiers de tâches ni les transcriptions des agents, seulement les sorties de plan-lint et les rapports du workflow. Messages courts. Toute étape qui lit des données de production ou personnelles réelles (dump de prod, base de prod ou copie) est un geste de l'utilisateur, avec le préfixe `!` : tu ne la lances jamais toi-même.

plan-lint, dans ce plugin : `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`. Le suivi : `node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs`, seul écrivain de `suivi.json` (hors git) et de la vue SUIVI.md ; les agents du workflow le lancent eux-mêmes, toi seulement pour les gestes décrits ici.

## 1. Pré-vol

Arrête-toi et explique ce qui manque si un point échoue.

1. `claude --version` : 2.1.271 ou plus. `node --version` : 18 ou plus.
2. Plugin : les agents `orchestre:worker`, `orchestre:worker-isole`, `orchestre:verificateur`, `orchestre:evaluateur`, `orchestre:integrateur`, `orchestre:replanificateur`, `orchestre:scribe`, `orchestre:lecteur-plan` et `orchestre:greffier` figurent parmi les types d'agents disponibles. Sinon : plugin désactivé ou pas rechargé, fais lancer `/reload-plugins`. Si le dépôt contient encore une installation manuelle (`.claude/skills/lancer/`, `.claude/workflows/executer-phase.js`, `.claude/orchestre/`), signale-la et propose `/orchestre:installer` pour la retirer ; ce n'est pas bloquant.
3. Réglages (`.claude/settings.local.json`, `.claude/settings.json`, `~/.claude/settings.json`) : `worktree.baseRef` vaut `head`, `autoContinueAtUsageLimit` est actif, `git push` est refusé, ainsi que l'outil de déploiement du projet s'il en a un. Sinon, propose `/orchestre:installer`. Si `Read(./.env.*)` est refusé sans les exceptions des modèles (`Read(!.env.example)`…), les agents ne pourront ni lire ni modifier les `.env.example` : signale-le et propose `/orchestre:installer` ; ce n'est pas bloquant. Les règles `Bash(node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs *)`, `Bash(node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs *)` et `Bash(node ${CLAUDE_PLUGIN_ROOT}/scripts/worktrees.mjs *)` doivent être dans `allow` de `.claude/settings.local.json` : si l'une manque (première utilisation ou mise à jour du plugin), propose en une ligne de l'ajouter en retirant les règles des scripts d'une version précédente, et fais-le après accord. Sans elles, chaque agent demanderait la permission de lancer sa commande de suivi ou de nettoyage, et le run se suspendrait. Même chose pour une règle du modèle de l'installeur ajoutée depuis l'installation, comme `Bash(git merge-base *)` (0.8.0, reprise de branche) : propose `/orchestre:installer`.
4. Lis `orchestre.config.json` du plan : branche d'intégration, branche de base (`branche_base`, `main` par défaut), parallélisme, mode par défaut, corrections, escalade, plafond de décisions d'office (`decisions_office_max`, 3 par défaut), plafond de contexte de cette session (`plafond_session_pilote`, 0,65 par défaut), préparation de l'environnement (`preparation`, `preparation_partagee`). Sans préparation, dis en une ligne que les dossiers de travail ne seront pas remis à jour (dépendances, code généré, base de test) et propose `/orchestre:pret <plan>`, qui la propose ; ce n'est pas bloquant.
5. Git : aucune modification non commitée sur les fichiers suivis. Si la branche d'intégration n'existe pas, crée-la depuis la branche de base ; place-toi dessus. Le dossier du plan doit y être commité, sinon les worktrees ne le verront pas. Si le projet a un `.env`, `.worktreeinclude` doit le lister. Puis `node ${CLAUDE_PLUGIN_ROOT}/scripts/worktrees.mjs nettoyer <plan>` : il retire les worktrees propres que les essais précédents ont laissés aux tâches du plan, et garde les branches ; recopie sa sortie. S'il refuse parce que `suivi.json` note un run « en-cours », demande à l'utilisateur si ce run est arrêté (session fermée sans fin de run) ; s'il l'est, relance avec `--run-arrete`. Un worktree gardé a des modifications : dis lesquelles l'utilisateur doit commiter ou annuler, sinon la tâche repartira sur une branche `-rN`. Ne le lance pas si un run de l'orchestrateur tourne déjà sur ce dépôt, depuis une autre session : ses agents y travaillent peut-être.
6. `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --integration <branche>`, plus `--base <branche_base>` si la config en donne une : aucune erreur. Affiche sa ligne d'estimation et son bloc « Prêt à lancer ». Ses avertissements (⚠) ne bloquent rien. Une commande composée, qu'un agent isolé dans un worktree se verra refuser : propose `/orchestre:pret <plan>` pour la réécrire. Une tâche sans `modele` (0.11.0) : son worker tournera sur sonnet et ses corrections suivront l'échelle d'escalade ; une tâche sans `raison_modele` : rien ne change pendant le run. Dis-le en une ligne, sans les détailler une à une ; `/orchestre:pret <plan>` les liste. Une tâche ou une escalade sur fable sans réglage `fable` : elle tournera sur fable ; propose `/orchestre:pret <plan>`, qui fait trancher l'utilisateur. Avec `"fable": false`, c'est une erreur, qui bloque.
   - PREREQUIS.md absent, ou sans ligne « Vérifié par /orchestre:pret » : propose de lancer `/orchestre:pret <plan>` d'abord. Ce n'est pas bloquant.
   - Des tâches de la première phase à lancer attendent un prérequis ouvert : dis lesquelles et ce qu'elles attendent. Propose de le régler maintenant, ou de lancer quand même : ces tâches attendront et le reste de la phase tournera. Si aucune tâche de la phase ne peut partir, ne lance pas. Régler une décision : outil de question, 4 options au plus (3 choix, le recommandé en premier, et « Reporter ») ; entrée `décision · majeur · <ID> : … (tranchée par l'utilisateur)` sous `## plan source` dans HANDOFF.md ; statut `fait` et preuve « HANDOFF » dans PREREQUIS.md ; si elle change une tâche pas encore lancée, montre l'amendement et écris-le après accord ; puis plan-lint et commit des fichiers du plan sur la branche d'intégration. Un geste : dis exactement ce que l'utilisateur doit faire (préfixe `!` pour ce qui touche un secret, des données réelles ou la prod), puis statut `fait` sur sa confirmation.
   - Prérequis `environnement` des tâches de la phase, déjà `fait` : relance leur preuve si c'est une commande sûre (sans écriture dans une base partagée, données réelles, appel payant ni arrêt de processus). En cas d'échec, dis-le et propose de le régler avant de lancer, ou de remettre le prérequis à `ouvert` : la tâche attendra.
7. Formateur et linter : si les vérifications ou un hook lancent un formateur ou un linter (Prettier, Biome, ESLint…), leurs exclusions (`.prettierignore`, `biome.json`, config ESLint…) doivent couvrir `plans/` et `.claude/`. Sinon, propose de les ajouter et commite sur la branche d'intégration : le scribe écrit dans `plans/`, et une vérification qui lit ces dossiers échouerait sur des fichiers qu'aucune tâche ne possède.
8. Suivi : `node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs vue <plan>`. Il régénère le tableau de SUIVI.md depuis le plan (colonnes de plan tirées du frontmatter, statuts relus dans SUIVI.md et git, cellules alignées, texte autour gardé) et crée `suivi.json` s'il manque. Une tâche fusionnée à la main sans la commande `pilote` y passe à « fusionnée ». S'il sort en erreur, montre-la et ne lance pas : l'ouverture du run échouerait de même (un statut hors des 7 dans SUIVI.md, par exemple). Si SUIVI.md a changé (`git status --porcelain -- <plan>/SUIVI.md`), montre les lignes qui changent autrement que par des espaces, puis commite-le seul sur la branche d'intégration après accord : `suivi : SUIVI.md régénéré par suivi.mjs`. Sans ce commit, le premier scribe l'emporterait dans le sien.

## 2. Choix de l'utilisateur

Avec l'outil de question, demande le mode (autonome, arrêt sur déviation, arrêt par phase ; défaut de la config : `mode_par_defaut`, qui vaut `auto`, `devia` ou `phase`) et le nombre de tâches simultanées (défaut de la config). En mode autonome, précise en une ligne que les points majeurs seront tranchés d'office (option la plus prudente), que tout point humain arrête le run, et que le run s'arrête aussi au-delà de `decisions_office_max` décisions d'office (config, 3 par défaut). Avec `--reprendre`, rappelle d'abord où en est le plan : `node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs etat <plan>`, recopié tel quel.

## 3. Boucle des phases

Pour chaque phase, en partant de la première qui a des tâches ni fusionnées ni annulées, commence par te placer à la racine du dépôt (`git rev-parse --show-toplevel`, puis `cd` sur le chemin rendu) : plan-lint, HANDOFF.md et le workflow s'y lisent en chemins relatifs.

1. Prêt : `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --phase <N> --integration <branche>` (plus `--base`). Pour une phase après la première, applique les mêmes règles qu'au pré-vol (point 6) aux prérequis de la phase.
2. Décisions : les entrées `décision` de HANDOFF.md, en une ligne chacune.
3. Lance le workflow `orchestre:executer-phase` (outil Workflow, paramètre `name`) avec `args` : `{ plan, phase, mode, parallelisme, integration, base, decisions, corrections_max, escalade, decisions_office_max, arbitrages, relancer, lint, prefixe_agents, suivi, preparation, preparation_partagee }`.
   - `mode` : `auto` (autonome), `devia` (arrêt sur déviation) ou `phase` (arrêt par phase), exactement ; toute autre valeur fait échouer le run.
   - `base` : `branche_base` de la config, seulement si elle en donne une.
   - `lint` : `${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`, tel quel. `suivi` : `${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs`, tel quel ; le workflow en déduit `worktrees.mjs`, dans le même dossier. `prefixe_agents` : `orchestre:`.
   - `preparation` et `preparation_partagee` : recopiées de la config, telles quelles ; omises si elle n'en a pas.
   - `decisions_office_max` : le plafond (config, 3 par défaut) moins les décisions d'office déjà prises depuis le début du run ou depuis le dernier arbitrage de l'utilisateur.
   - `arbitrages` : les options choisies par l'utilisateur depuis le dernier rapport, `[{ tache, titre, option }]`, `option` recopiée telle quelle depuis le rapport ; sinon `[]`. Le workflow les fait écrire par le scribe avant de lire le plan : ne les écris pas toi-même. Ne repasse jamais un arbitrage listé dans `arbitrages_appliques` (même tâche, même titre, même option).
   - `relancer` : les tâches au statut « besoin-humain » que l'utilisateur a décidé de faire repartir, une fois fait ce qui revenait à un humain ; sinon `[]`. Sans cela, une tâche en attente d'un humain ne repart pas.
4. À réception du rapport, ajoute ses `decisions_office` et ses `amendements_ecartes` à la liste du run. Recopie le champ `worktrees` du rapport, s'il en a un : un worktree gardé attend un geste de l'utilisateur (commit ou abandon de ses modifications). Si `suivi_echecs` n'est pas vide, dis-le en une ligne (tâche, étape, erreur) : une étape ratée ne fausse que l'affichage ; une clôture ou un arbitrage raté a déjà arrêté le run ; un `fin-run` raté laisse le run « en-cours » dans `suivi.json`, et le run suivant le passera « interrompu ». Puis :
   - `terminé` : en mode autonome ou déviation, passe à la phase suivante sans attendre. En mode par phase, fais d'abord trancher les `points_a_trancher`, puis pose la question de fin de phase avec l'outil de question. Le texte même de la question commence par le résumé de la phase, 5 lignes au plus : tâches, corrections et raison de chaque refus (champ `refus`), écarts, découvertes, critères non vérifiables (champ `non_verifiables`), prérequis encore ouverts pour la phase suivante (relance plan-lint avec `--phase` sur la phase suivante pour les connaître), relectures ajoutées (champ `relectures`), tokens à lire dans `/workflows`. Le résumé ne va jamais seulement dans un message à part.
   - `à-relancer` : des tâches ont été ajoutées à la phase, ou reportées (`reportees`) parce qu'elles dépendent d'une tâche ajoutée. Relance la même phase sans attendre, deux fois de suite au plus ; au-delà, demande.
   - `arbitrage` : fais trancher le point `arbitrage`, puis les `points_a_trancher`. S'il porte `coupe_circuit`, dis que le plafond de décisions d'office est atteint et liste celles du run. S'il porte `incoherence`, dis que l'option recommandée citait des tâches que rien ne crée, puis fais trancher. S'il porte `humain`, dis précisément ce qu'un humain doit faire ; pour un contrôle post-fusion en échec, propose de réparer ici sur la branche d'intégration (2 passes vertes des vérifications de la tâche) avant de relancer. Relance ensuite la même phase avec les options choisies dans `arbitrages` et, si la décision fait repartir une tâche en attente d'un humain, avec son id dans `relancer` ; sauf si l'utilisateur choisit d'arrêter : va alors à la fin.
   - `partiel` : pour chaque tâche de `en_attente` (statut « besoin-humain »), dis ce qu'un humain doit faire d'après HANDOFF.md ; elle ne repartira que dans `relancer`. Pour chaque tâche de `en_attente_prerequis`, dis quel prérequis de PREREQUIS.md elle attend ; elle repartira d'elle-même au prochain run une fois ce prérequis `fait`, sans passer par `relancer`, sauf si elle est aussi « besoin-humain » dans SUIVI.md : mets-la alors aussi dans `relancer`. Si le rapport a des `reportees` ou des `taches_ajoutees` de la phase en cours, relance d'abord la phase sans attendre, deux fois de suite au plus : elles partiront. Pour chaque tâche bloquée ou en échec, donne la raison exacte (son worktree a pu être retiré en fin de run : sa branche reste, c'est elle qu'on corrige) (champ `blocage` du rapport, pas le résumé du worker) et, s'il y en a, les refus des essais précédents (champ `refus`), puis propose : corriger ici sur sa branche, relancer la phase, ou arrêter. Après une correction faite ici : 2 passes vertes des vérifications, puis une évaluation par l'agent `orchestre:evaluateur` (définition du fini, diff, résultats des vérifications, rapport de correction), et seulement si elle est OK, fusion `--no-ff` dans la branche d'intégration avec le message « tâche <id> : <titre> », statut « fusionnée » par le suivi (geste du pilote, plus bas), puis relance de la phase : les tâches restantes partiront seules.
   - `erreur`, ou run interrompu : explique, puis propose de lancer un **nouveau** run de la phase, jamais la reprise du run interrompu. plan-lint et l'historique git sautent les tâches déjà fusionnées. Un `detail` qui commence par « suivi : run non ouvert » : le script a refusé d'ouvrir le run et aucune tâche n'est partie ; montre son erreur et règle-la d'abord (`suivi.json` illisible : supprime-le, il se reconstruit depuis SUIVI.md, HANDOFF.md et git). Les arbitrages ne sont pas appliqués : repasse-les.

   Faire trancher un point : outil de question, une option par choix, la recommandée en premier, avec son impact. Un point sans option attend une réponse libre, à passer comme option `{ id: "humain", description: <réponse> }`. Les `points_a_trancher` se tranchent avant le run suivant, quel que soit le statut.

   Gestes du pilote sur le suivi, entre deux runs et jamais pendant : SUIVI.md ne s'édite plus à la main. Une tâche fusionnée à la main, ou que l'utilisateur annule, passe par `node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs pilote <plan> --json '{"tache":"<id>","statut":"fusionnée","raison":"<raison>"}'` (ou `"statut":"annulée"`), puis commit de SUIVI.md seul sur la branche d'intégration : `suivi(<id>) : <statut> à la main`. Pas d'apostrophe dans la raison, ou écrite `\u0027`.

## 4. Fin

Résumé final : tâches fusionnées, branche d'intégration prête pour une PR, entrées majeures de HANDOFF.md, recommandations de contexte. Liste à part, en premier, les décisions prises d'office (tâche, point, option retenue), les amendements non appliqués et les gestes faits à la main hors de la boucle évaluée : ce sont les premiers points à relire dans la PR. Liste ensuite les entrées `relecture` de HANDOFF.md, à faire par l'utilisateur avant la PR : les fichiers que les agents n'ont pas le droit de lire ou d'écrire, à relire ou modifier, et les commandes qu'ils n'ont pas le droit de lancer. Pour les fichiers, donne-lui la commande à lancer lui-même dans un terminal à part (`git diff <branche_base>...<branche d'intégration> -- <fichiers>`) : ne l'affiche pas toi-même, un secret glissé dans l'un de ces fichiers entrerait dans ton contexte. Liste ensuite les entrées `ticket` de HANDOFF.md, à ouvrir après la PR. Termine par un tableau par tâche, qui mesure le coût et la qualité de la réalisation : essais, refus des évaluations, corrections, écarts majeurs, décisions d'office, gestes faits à la main ; les tokens de chaque tâche se lisent dans `/workflows`. Tu ne fusionnes jamais dans `main` et tu ne pousses jamais.

## Pendant un run

Les agents travaillent dans le checkout principal. Tant qu'un run tourne, tu n'y touches pas : aucun `git switch`, `checkout`, `stash`, `reset` ni commit, aucune écriture de fichier, et `git status` seulement avec `GIT_OPTIONAL_LOCKS=0`. Une commande qui compare deux commits (`git diff <a>...<b>`, `git log`) reste permise. Si l'utilisateur demande autre chose sur le dépôt, dis-lui que tu le feras à la fin du run, puis fais-le à ce moment-là. Pour savoir où en est le plan, `/orchestre:etat` lit seulement et peut tourner pendant le run ; `node ${CLAUDE_PLUGIN_ROOT}/scripts/suivi.mjs etat <plan>` aussi, et montre en plus l'étape de chaque tâche en cours.

## Contexte

Si ton contexte approche le plafond de la config (`plafond_session_pilote`, 0,65 par défaut), termine la phase en cours, puis propose de reprendre dans une session neuve avec `/orchestre:lancer <plan> --reprendre`. L'état est entièrement dans le plan et dans git.
