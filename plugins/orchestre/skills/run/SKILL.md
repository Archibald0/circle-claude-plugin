# Run a plan

You pilot the execution of `$ARGUMENTS`. You stay light: you read neither the task files nor the agents' transcripts, only the outputs of plan-lint and the workflow's reports. Short messages. Any step that reads real production or personal data (production dump, production database or a copy) is an action of the user, with the prefix `!`: you never run it yourself.

Language: until you know the plan's language (pre-flight, point 5), and for a plan of orchestre 0.11 not migrated yet, talk to the user in the language of the conversation. From then on, talk to the user and write the free text you add to the plan (HANDOFF descriptions, Prerequisite and Evidence cells) in the plan's language: `language` of `orchestre.config.json`, `"en"` when absent, `"fr"` for a plan migrated from orchestre 0.11. Keys, values, section titles and commit messages stay in English.

plan-lint, in this plugin: `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`. Progress: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs`, sole writer of `progress.json` (outside git) and of the PROGRESS.md view; the workflow's agents run it themselves, you only for the actions described here.

## 1. Pre-flight

Stop and explain what is missing if a point fails.

1. `claude --version`: 2.1.271 or later. `node --version`: 18 or later.
2. Plugin: the agents `orchestre:worker`, `orchestre:isolated-worker`, `orchestre:verifier`, `orchestre:evaluator`, `orchestre:integrator`, `orchestre:replanner`, `orchestre:scribe`, `orchestre:plan-reader` and `orchestre:clerk` are among the available agent types. Otherwise: plugin disabled or not reloaded, have `/reload-plugins` run. If the repository still holds a manual install (`.claude/skills/lancer/`, `.claude/workflows/executer-phase.js`, `.claude/orchestre/`), report it and offer `/orchestre:install` to remove it; it is not blocking.
3. Settings: `node ${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs check` (below, `settings.mjs`), which compares the settings of Claude Code (`.claude/settings.local.json`, `.claude/settings.json`, user settings) with the model of `/orchestre:install`, rule by rule: `worktree.baseRef` at `head`, `Workflow(orchestre:run-phase)`, the rules of the plugin's scripts for this version, the agents' git commands, `git push` denied, the `.env` denied except their templates. It also lists the rules of an older install to remove, those of orchestre 0.11 included. Without these rules, each agent would ask for permission to run its progress or cleanup command, and the run would be suspended. Copy its output.
   - "settings complete": go on; its warnings (`⚠`) block nothing.
   - "settings missing": orchestre was never installed in this repository. Stop: say to run `/orchestre:install`, then `/orchestre:run <plan>` again.
   - "settings incomplete" (an older install, or the plugin updated since, whose scripts have another path): offer, with the question tool, to write what it lists ("Yes (recommended)", "No"); after agreement, `settings.mjs apply`, copy its first line and go on: Claude Code reloads the permission rules of its settings files during the session. If `worktree.baseRef` was among the lines, its reload is not documented: offer to go on in a new session (`/orchestre:run <plan>`). Exit code 3: the Bash sandbox refuses writes to the settings files; give the user the command to run at the prompt prefixed with `!` (`node ${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs apply`), then run `settings.mjs check` again. If the user declines: stop, and say to run `/orchestre:install`.
   - Exit code 2: show the error and stop; a settings file that is not valid JSON is for the user to fix.
   - Outside the script: the project's deployment tool, if it has one, must be denied too (`Bash(<tool> *)`); otherwise, offer `/orchestre:install`.
4. Git and plan format:
   - No uncommitted change on tracked files. Integration branch: `integration_branch` of the plan's `orchestre.config.json` (`branche_integration` in a plan of orchestre 0.11); base branch: `base_branch` (`branche_base` in 0.11), `main` by default. If the integration branch does not exist, create it from the base branch; switch to it. The plan folder must be committed on it, otherwise the worktrees will not see it.
   - Plan format: `node ${CLAUDE_PLUGIN_ROOT}/scripts/migrate.mjs <plan>`, from the main checkout, on the integration branch. Without option, it only reads: if it answers "already in the 0.12 format, nothing to migrate", go on. Otherwise the plan, or part of it, is still in the French format of orchestre 0.11 or earlier (`<plan>/taches/`, or `SUIVI.md`, `PREREQUIS.md`, `suivi.json` or French keys left next to `<plan>/tasks/` by another clone), which the scripts of this version refuse. Show its summary of the changes and say in one line that keys, values, file names and section titles move to English, that the free text stays as written and the plan gets `"language": "fr"`, and that the git history of 0.11 (branches `tache/*`, commits "tâche <id> : ") is not rewritten. After agreement, run it again with `--write`: it migrates and commits the plan folder alone (`orchestre: migrate plan <name> to the 0.12 format`); copy its last lines. If it refuses because `suivi.json` marks a run "en-cours", ask the user whether that run is stopped (session closed without a run end); if it is, run it again with `--write --run-stopped`, and that answer also holds for `worktrees.mjs clean` at point 6. Any other refusal or error, or a commit refused by a hook (code 1, files migrated and staged): show the message and stop. If the user declines the migration: stop, the plan cannot run in that format.
   - After a migration: `git branch --list "tache/*" --no-merged <integration branch>`, keeping the plan's task ids. These tasks were started in 0.11 and not merged: say in one line that they will not be taken back, that they start again from the integration branch on `task/<id>`, and that the old branch stays in git, for reference.
5. Read `orchestre.config.json` of the plan: integration branch (`integration_branch`), base branch (`base_branch`, `main` by default), parallelism (`max_parallelism`), default mode (`default_mode`), fixes (`max_fixes`), escalation (`escalation`), cap on auto-decisions (`max_auto_decisions`, 3 by default), context cap of this session (`pilot_context_cap`, 0.65 by default), language (`language`, `"en"` by default), environment setup (`setup`, `shared_setup`). Without a setup, say in one line that the working folders will not be brought up to date (dependencies, generated code, test database) and offer `/orchestre:ready <plan>`, which proposes one; it is not blocking.
6. If the project has a `.env`, `.worktreeinclude` must list it. Then `node ${CLAUDE_PLUGIN_ROOT}/scripts/worktrees.mjs clean <plan>`: it removes the clean worktrees that earlier attempts left to the plan's tasks, and keeps the branches; copy its output. If the user said at the migration (point 4) that the run is stopped, run it with `--run-stopped` straight away. Otherwise, if it refuses because `progress.json` marks a run "in-progress", ask the user whether that run is stopped (session closed without a run end); if it is, run it again with `--run-stopped`. A kept worktree has changes: say which ones the user must commit or discard, otherwise the task will start again on a `-rN` branch. Do not run it if a run of the orchestrator is already working on this repository, from another session: its agents may be working there.
7. `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --integration <branch>`, plus `--base <base_branch>` if the config gives one: no error. Show its estimate line and its "Ready to run" block. Its warnings (⚠) block nothing. A compound command, which an agent isolated in a worktree will see refused: offer `/orchestre:ready <plan>` to rewrite it. A task without `model`: its worker will run on sonnet and its fixes will follow the escalation ladder; a task without `model_reason`: nothing changes during the run. Say it in one line, without detailing them one by one; `/orchestre:ready <plan>` lists them. A task or an escalation on fable without a `fable` setting: it will run on fable; offer `/orchestre:ready <plan>`, which has the user settle it. With `"fable": false`, it is an error, which blocks.
   - PREREQUISITES.md missing, or without a line "Checked by /orchestre:ready": offer to run `/orchestre:ready <plan>` first. It is not blocking.
   - Tasks of the first phase to run wait for an open prerequisite: say which ones and what they wait for. Offer to settle it now, or to run anyway: these tasks will wait and the rest of the phase will run. If no task of the phase can start, do not run. Settling a decision: question tool, 4 options at most (3 choices, the recommended one first, and "Defer"); entry `decision · major · <ID>: … (settled by the user)` under `## source plan` in HANDOFF.md; status `done` and evidence "HANDOFF" in PREREQUISITES.md; if it changes a task not started yet, show the amendment and write it after agreement; then plan-lint, and a commit of the plan files on the integration branch. A manual action: say exactly what the user must do (prefix `!` for what touches a secret, real data or production), then status `done` on their confirmation.
   - `environment` prerequisites of the phase's tasks, already `done`: run their evidence again if it is a safe command (no write into a shared database, no real data, no paid call and no stopping of a process). If it fails, say so and offer to settle it before running, or to set the prerequisite back to `open`: the task will wait.
8. Formatter and linter: if the verifications or a hook run a formatter or a linter (Prettier, Biome, ESLint…), their exclusions (`.prettierignore`, `biome.json`, ESLint config…) must cover `plans/` and `.claude/`. Otherwise, offer to add them and commit on the integration branch, with the message `chore: exclude plans/ and .claude/ from the formatter and linter`: the scribe writes into `plans/`, and a verification that reads these folders would fail on files no task owns.
9. Progress: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs view <plan>`. It regenerates the table of PROGRESS.md from the plan (plan columns taken from the frontmatter, statuses reread from PROGRESS.md and git, cells aligned, text around kept) and creates `progress.json` if it is missing. A task merged by hand without the `pilot` command moves to "merged" there. If it exits with an error, show it and do not run: the run start would fail the same way (a status outside the 7 in PROGRESS.md, for example). If PROGRESS.md changed (`git status --porcelain -- <plan>/PROGRESS.md`), show the rows that change other than by spaces, then commit it alone on the integration branch after agreement: `progress: PROGRESS.md regenerated by progress.mjs`. Without that commit, the first scribe would carry it into its own.

## 2. The user's choices

With the question tool, ask for the mode (autonomous, stop on deviation, stop at each phase; default from the config: `default_mode`, which is `auto`, `deviation` or `phase`) and the number of simultaneous tasks (default from the config). In autonomous mode, say in one line that major issues will be settled automatically (safest option), that any human issue stops the run, and that the run also stops beyond `max_auto_decisions` auto-decisions (config, 3 by default). With `--resume`, first recall where the plan stands: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs status <plan>`, copied as is.

## 3. Loop over the phases

For each phase, starting from the first one that has tasks neither merged nor cancelled, first place yourself at the root of the repository (`git rev-parse --show-toplevel`, then `cd` to the path returned): plan-lint, HANDOFF.md and the workflow read relative paths from there.

1. Ready: `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --phase <N> --integration <branch>` (plus `--base`). For a phase after the first, apply to the phase's prerequisites the same rules as at the pre-flight (point 7).
2. Decisions: the `decision` entries of HANDOFF.md, one line each.
3. Launch the workflow `orchestre:run-phase` (Workflow tool, parameter `name`) with `args`: `{ plan, phase, mode, parallelism, integration, base, decisions, max_fixes, escalation, max_auto_decisions, rulings, rerun, lint, agent_prefix, progress, setup, shared_setup, language }`.
   - `mode`: `auto` (autonomous), `deviation` (stop on deviation) or `phase` (stop at each phase), exactly; any other value makes the run fail.
   - `base`: `base_branch` of the config, only if it gives one.
   - `lint`: `${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`, as is; required, the workflow refuses to start without it. `progress`: `${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs`, as is; the workflow derives `worktrees.mjs` from it, in the same folder. `agent_prefix`: `orchestre:`.
   - `language`: `language` of the config, as is, `"en"` when absent. The workflow does not read the plan's own: it writes this one in the agents' prompts.
   - `setup` and `shared_setup`: copied from the config, as is; left out if it has none.
   - `max_auto_decisions`: the cap (config, 3 by default) minus the auto-decisions already taken since the start of the run or since the user's last ruling.
   - `rulings`: the options the user chose since the last report, `[{ task, title, option }]`, `task` and `title` those of the issue, `option` copied as is from the report, actions included; otherwise `[]`. The workflow has the scribe write them before reading the plan: do not write them yourself. Never pass again a ruling listed in `rulings_applied` (same task, same title, same option id).
   - `rerun`: the tasks with the status "needs-human" that the user decided to restart, once done what was for a human; otherwise `[]`. Without it, a task that waits for a human does not start again.
4. On receiving the report, add its `auto_decisions` and its `discarded_amendments` to the run's list. Copy the report's `worktrees` field, if it has one: a kept worktree waits for an action of the user (commit or discard of its changes). If `progress_failures` is not empty, say it in one line per failure (`task`, `step`, `error`): a failed step only spoils the display; a failed close or ruling has already stopped the run; a failed `run-end` leaves the run "in-progress" in `progress.json`, and the next run will turn it "interrupted". Then, by `status`:
   - `finished`: in autonomous or deviation mode, go on to the next phase without waiting. In phase mode, first have the `open_issues` settled, then ask the end-of-phase question with the question tool. The text of the question itself starts with the summary of the phase, 5 lines at most: tasks, fixes and the reason of each rejection (field `rejections`), deviations, findings, criteria that could not be verified (field `unverifiable`), prerequisites still open for the next phase (run plan-lint with `--phase` on the next phase to know them), reviews added (field `reviews`), tokens to read in `/workflows`. The summary never goes only into a separate message.
   - `rerun`: tasks were added to the phase, or deferred (`deferred`) because they depend on an added task. Rerun the same phase without waiting, twice in a row at most; beyond that, ask.
   - `awaiting-ruling`: have the issue `stop_issue` settled, then the `open_issues`. If it carries `circuit_breaker`, say that the cap on auto-decisions is reached and list those of the run. If it carries `inconsistency`, say that the recommended option cited tasks that nothing creates, then have it settled. If it carries `human`, say precisely what a human must do. A post-merge check that failed has the options `repair` (recommended) and `stop`, and its task stays merged: on `repair`, repair here, on the integration branch, until two green passes of the task's verifications, commit, then rerun the phase with this ruling in `rulings`; on `stop`, go to the end. For any other issue, rerun the same phase with the chosen options in `rulings` and, if the decision restarts a task that waits for a human, with its id in `rerun`; unless the user chooses to stop: go to the end then.
   - `partial`: for each task of `waiting` (status "needs-human"), say what a human must do, from HANDOFF.md; it will only start again in `rerun`. For each task of `waiting_on_prerequisites`, say which prerequisite of PREREQUISITES.md it waits for; it will start again on its own at the next run once that prerequisite is `done`, without going through `rerun`, unless it is also "needs-human" in PROGRESS.md: then put it in `rerun` too. If the report has `deferred` tasks or `added_tasks` of the current phase, first rerun the phase without waiting, twice in a row at most: they will start. For each blocked or failed task, give the exact reason (field `blocker` of the report, not the worker's summary) and, if there are any, the rejections of the earlier attempts (field `rejections`), then offer: fix it here on its branch, rerun the phase, or stop. Its branch: `branch` of the report (its worktree may have been removed at the end of the run: the branch stays, it is the one to fix). If `branch` is null or missing from git, take the most recent of `git branch --list "task/<id>*" --sort=-committerdate`; if there is none, for a plan migrated from orchestre 0.11, the most recent of `git branch --list "tache/<id>*" --sort=-committerdate` (`migrate.mjs` rewrites the plan's text, never the branches of git). A branch of an earlier run is first brought up to date with the integration branch (`git merge <integration branch>`, never a rebase). After a fix made here: two green passes of the verifications, then an evaluation by the agent `orchestre:evaluator` (definition of done, diff, results of the verifications, report of the fix), and only if its verdict is `pass`, a `--no-ff` merge into the integration branch with the message "task <id>: <title>" (the title without quote, backtick, dollar or backslash), status "merged" through progress (pilot's action, below), then a rerun of the phase: the remaining tasks will start on their own.
   - `error`, or a run interrupted: explain, then offer to launch a **new** run of the phase, never to resume the interrupted run. plan-lint and git history skip the tasks already merged. A `detail` that starts with "progress: run not opened": the script refused to open the run and no task started; show its error and settle it first (`progress.json` unreadable: delete it, it is rebuilt from PROGRESS.md, HANDOFF.md and git). The rulings were not applied: pass them again.

   Having an issue settled: question tool, one option per choice, the recommended one first, with its impact. An issue without an option expects a free answer. A free answer, "Other" included, is passed as the option `{ id: "human", description: <answer> }`. The `open_issues` are settled before the next run, whatever the status.

   Tasks the pilot writes, between two runs and never during one: when a ruling, an evaluation on a real model or the user asks for work that no remaining task covers, first amend a task not yet started (status `todo` or `added`) that owns the files concerned, with criteria and verifications added. Otherwise apply the plan's splitting rule ("Own task only for a reason" in `${CLAUDE_PLUGIN_ROOT}/skills/prepare/format.md`): one task per module, one criterion of done per finding. When two of the tasks you would write share files, ask with the question tool "Group these <N> findings?", with "One task per module (recommended)" and "One task per finding", each option giving the number of tasks it writes. Write them on the task template of that format (a free id, `model` and `model_reason`, owned files, verification, definition of done), run plan-lint until "valid plan", then commit the task files alone on the integration branch: `plan(<n>): add <ids>`.

   Pilot's actions on progress, between two runs and never during one: PROGRESS.md is no longer edited by hand. A task merged by hand, or that the user cancels, goes through `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs pilot <plan> --json '{"task":"<id>","status":"merged","reason":"<reason>"}'` (or `"status":"cancelled"`), then a commit of PROGRESS.md alone on the integration branch: `progress(<id>): <status> by hand`. No apostrophe in the reason, or written `\u0027`.

## 4. End

Final summary: tasks merged, integration branch ready for a PR, major entries of HANDOFF.md, context recommendations. List apart, first, the auto-decisions (task, issue, option kept), the amendments not applied and the actions done by hand outside the evaluated loop: they are the first points to review in the PR. Then list the `review` entries of HANDOFF.md, for the user to do before the PR: the files the agents may not read or write, to review or change, and the commands they may not run. For the files, give the user the command to run themselves in a separate terminal (`git diff <base_branch>...<integration branch> -- <files>`): do not show it yourself, a secret slipped into one of these files would enter your context. Then list the `ticket` entries of HANDOFF.md, to open after the PR. End with a table per task, which measures the cost and the quality of the work: attempts, rejections of the evaluations, fixes, major deviations, auto-decisions, actions done by hand; the tokens of each task can be read in `/workflows`. You never merge into `main` and you never push.

## During a run

The agents work in the main checkout. While a run is going on, you do not touch it: no `git switch`, `checkout`, `stash`, `reset` or commit, no file write, and `git status` only with `GIT_OPTIONAL_LOCKS=0`. A command that compares two commits (`git diff <a>...<b>`, `git log`) stays allowed. If the user asks for something else on the repository, tell them you will do it at the end of the run, then do it at that moment. To know where the plan stands, `/orchestre:status` only reads and can run during the run; `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs status <plan>` too, and also shows the step of each task in progress.

## Context

If your context approaches the cap of the config (`pilot_context_cap`, 0.65 by default), finish the current phase, then offer to go on in a new session with `/orchestre:run <plan> --resume`. The state is entirely in the plan and in git.
