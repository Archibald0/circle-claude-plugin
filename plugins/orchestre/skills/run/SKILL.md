# Run a plan

You pilot the execution of `$ARGUMENTS`. You stay light: you read neither the task files nor the agents' transcripts, only the outputs of plan-lint and the workflow's reports. Short messages. Any step that reads real production or personal data (production dump, production database or a copy) is an action of the user, with the prefix `!`: you never run it yourself.

Language: until you know the plan's language (pre-flight, point 5), and for a plan of orchestre 0.11 not migrated yet, talk to the user in the language of the conversation. From then on, talk to the user and write the free text you add to the plan (HANDOFF descriptions, Prerequisite and Evidence cells) in the plan's language: `language` of `orchestre.config.json`, `"en"` when absent, `"fr"` for a plan migrated from orchestre 0.11. Keys, values, section titles and commit messages stay in English.

plan-lint, in this plugin: `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`. Progress: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs`, sole writer of `progress.json` (outside git) and of the PROGRESS.md view; the workflow's agents run it themselves, you only for the actions described here.

## 1. Pre-flight

Stop and explain what is missing if a point fails.

1. `claude --version`: 2.1.271 or later. `node --version`: 18 or later.
2. Plugin: the agents `orchestre:worker`, `orchestre:isolated-worker`, `orchestre:verifier`, `orchestre:evaluator`, `orchestre:integrator`, `orchestre:replanner`, `orchestre:scribe`, `orchestre:plan-reader`, `orchestre:clerk` and `orchestre:challenger` are among the available agent types. Otherwise: plugin disabled or not reloaded, have `/reload-plugins` run. If the repository still holds a manual install (`.claude/skills/lancer/`, `.claude/workflows/executer-phase.js`, `.claude/orchestre/`), report it and offer `/orchestre:install` to remove it; it is not blocking.
3. Settings: `node ${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs check` (below, `settings.mjs`), which compares the settings of Claude Code (`.claude/settings.local.json`, `.claude/settings.json`, user settings) with the model of `/orchestre:install`, rule by rule: `worktree.baseRef` at `head`, `Workflow(orchestre:run-phase)`, the rules of the plugin's scripts for this version, the agents' git commands, `git push` denied, the `.env` denied except their templates. It also lists the rules of an older install to remove, those of orchestre 0.11 included. Without these rules, each agent would ask for permission to run its progress or cleanup command, and the run would be suspended. Copy its output.
   - "settings complete": go on; its warnings (`⚠`) block nothing.
   - "settings missing": orchestre was never installed in this repository. Stop: say to run `/orchestre:install`, then `/orchestre:run <plan>` again.
   - "settings incomplete" (an older install, or the plugin updated since, whose scripts have another path): offer, with the question tool, to write what it lists ("Yes (recommended)", "No"); after agreement, `settings.mjs apply`, copy its first line and go on: Claude Code reloads the permission rules of its settings files during the session. If `worktree.baseRef` was among the lines, its reload is not documented: offer to go on in a new session (`/orchestre:run <plan>`). Exit code 3: the Bash sandbox refuses writes to the settings files; give the user the command to run at the prompt prefixed with `!` (`node ${CLAUDE_PLUGIN_ROOT}/scripts/settings.mjs apply`), then run `settings.mjs check` again. If the user declines: stop, and say to run `/orchestre:install`.
   - Exit code 2: show the error and stop; a settings file that is not valid JSON is for the user to fix.
   - Outside the script: the project's deployment tool, if it has one, must be denied too (`Bash(<tool> *)`); otherwise, offer `/orchestre:install`.
4. Git and plan format:
   - No uncommitted change on tracked files. Integration branch: `integration_branch` of the plan's `orchestre.config.json` (`branche_integration` in a plan of orchestre 0.11); base branch: `base_branch` (`branche_base` in 0.11), `main` by default. If the integration branch does not exist, create it from the base branch; switch to it. The plan folder must be committed on it, otherwise the worktrees will not see it.
   - Plan format: `node ${CLAUDE_PLUGIN_ROOT}/scripts/migrate.mjs <plan>`, from the main checkout, on the integration branch. Without option, it only reads: if it answers "already in the 0.12 format, nothing to migrate", go on. Otherwise the plan, or part of it, is still in the French format of orchestre 0.11 or earlier (`<plan>/taches/`, or `SUIVI.md`, `PREREQUIS.md`, `suivi.json` or French keys left next to `<plan>/tasks/` by another clone), which the scripts of this version refuse. Show its summary of the changes and say in one line that keys, values, file names and section titles move to English, that the free text stays as written and the plan gets `"language": "fr"`, and that the git history of 0.11 (branches `tache/*`, commits "tâche <id> : ") is not rewritten. After agreement, run it again with `--write`: it migrates and commits the plan folder alone (`orchestre: migrate plan <name> to the 0.12 format`); copy its last lines. If it refuses because `suivi.json` marks a run "en-cours", ask the user whether that run is stopped (session closed without a run end); if it is, run it again with `--write --run-stopped`, and that answer also holds for `worktrees.mjs clean` at point 6. Any other refusal or error, or a commit refused by a hook (code 1, files migrated and staged): show the message and stop. If the user declines the migration: stop, the plan cannot run in that format.
   - After a migration: `git branch --list "tache/*" --no-merged <integration branch>`, keeping the plan's task ids. These tasks were started in 0.11 and not merged: say in one line that they will not be taken back, that they start again from the integration branch on `task/<id>`, and that the old branch stays in git, for reference.
   - Rulings recorded outside a run: first list what apply would write, from `progress.json`: its `pending_rulings` (`issue`, and the option or `a free answer`) and its `pending_done` (`prerequisite`), one line each, and offer to withdraw any of them, with `progress.mjs unrule` (`{"issue":"<id>"}`) or `progress.mjs undid` (`{"prerequisite":"<id>"}`), in a quoted heredoc as for `rule` (section 3); once applied, they can no longer be withdrawn. With nothing listed, say nothing. Then `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs apply <plan>`, from the main checkout, on the integration branch, once the plan is committed on it and in the 0.12 format, and before the checks of points 5 to 8, so that they see the rulings and the prerequisites it settles (a prerequisite noted done with `did`, a decision ruled outside a run). It reports into the plan, in one commit `progress: rulings <ids>`, the rulings recorded with `rule` (by you or from the `/progress` pane) and the prerequisites noted done with `did`. Copy its output. With nothing recorded it writes nothing (`no ruling to apply`). Say in one line what it applied (`applied`, and `done` for the prerequisites). The rulings it applies here are recorded in the run that the next run start opens: they come back in its `rulings_applied`, in `progress.json` and in the return, and in the decisions given to the agents. A ruling it refuses (`rejected`) is said with its reason, and its issue is settled again as in section 3. Code 1: nothing is written and the rulings stay recorded; show its message and do not run. `/orchestre:ready` only reports these rulings, it never applies them.
5. Read `orchestre.config.json` of the plan: integration branch (`integration_branch`), base branch (`base_branch`, `main` by default), parallelism (`max_parallelism`), default mode (`default_mode`), fixes (`max_fixes`), escalation (`escalation`), cap on auto-decisions (`max_auto_decisions`, 3 by default), wait for a ruling (`ruling_wait_minutes`, 15 by default, 0 to never wait), context cap of this session (`pilot_context_cap`, 0.65 by default), language (`language`, `"en"` by default), environment setup (`setup`, `shared_setup`). Without a setup, say in one line that the working folders will not be brought up to date (dependencies, generated code, test database) and offer `/orchestre:ready <plan>`, which proposes one; it is not blocking.
6. If the project has a `.env`, `.worktreeinclude` must list it. Then `node ${CLAUDE_PLUGIN_ROOT}/scripts/worktrees.mjs clean <plan>`: it removes the clean worktrees that earlier attempts left to the plan's tasks, and keeps the branches; copy its output. Do not run `clean` if a run of the orchestrator is already working on this repository, from another session: its agents may be working in those worktrees. If the user said at the migration (point 4) that the run is stopped, run it with `--run-stopped` straight away. Otherwise, if it refuses because `progress.json` marks a run "in-progress", ask the user whether that run is stopped (session closed without a run end); if it is, run it again with `--run-stopped`. A kept worktree has changes: say which ones the user must commit or discard, otherwise the task will start again on a `-rN` branch. Then `node ${CLAUDE_PLUGIN_ROOT}/scripts/worktrees.mjs space <plan> --parallelism <n>`, `n` being `max_parallelism` of the config, which only reads: copy its line as is. Its `⚠` (the free disk space may not hold one copy of the working folder per parallel task) and its `not measured` block nothing: say it in one line and go on.
7. `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --integration <branch>`, plus `--base <base_branch>` if the config gives one: no error. An error "a branch task/<id> already exists": offer `/orchestre:ready <plan>`, which gives the plan a free prefix. Show its estimate line and its "Ready to run" block. Its warnings (⚠) block nothing. A compound command, which an agent isolated in a worktree will see refused: offer `/orchestre:ready <plan>` to rewrite it. A task without `model`: its worker will run on sonnet and its fixes will follow the escalation ladder; a task without `model_reason`: nothing changes during the run. Say it in one line, without detailing them one by one; `/orchestre:ready <plan>` lists them. A task or an escalation on fable without a `fable` setting: it will run on fable; offer `/orchestre:ready <plan>`, which has the user settle it. With `"fable": false`, it is an error, which blocks.
   - PREREQUISITES.md missing, or without a line "Checked by /orchestre:ready": offer to run `/orchestre:ready <plan>` first. It is not blocking.
   - Tasks of the first phase to run wait for an open prerequisite: say which ones and what they wait for. Offer to settle it now, or to run anyway: these tasks will wait and the rest of the phase will run. If no task of the phase can start, do not run. Settling a decision: question tool, 4 options at most (3 choices, the recommended one first, and "Defer"); entry `decision · major · <ID>: … (settled by the user)` under `## source plan` in HANDOFF.md; status `done` and evidence "HANDOFF" in PREREQUISITES.md; if it changes a task not started yet, show the amendment and write it after agreement; then plan-lint, and a commit of the plan files on the integration branch. A manual action: say exactly what the user must do (prefix `!` for what touches a secret, real data or production), then status `done` on their confirmation.
   - `environment` prerequisites of the phase's tasks, already `done`: run their evidence again if it is a safe command (no write into a shared database, no real data, no paid call and no stopping of a process). If it fails, say so and offer to settle it before running, or to set the prerequisite back to `open`: the task will wait.
8. Formatter and linter: if the verifications or a hook run a formatter or a linter (Prettier, Biome, ESLint…), their exclusions (`.prettierignore`, `biome.json`, ESLint config…) must cover `plans/` and `.claude/`. Otherwise, offer to add them and commit on the integration branch, with the message `chore: exclude plans/ and .claude/ from the formatter and linter`: the scribe writes into `plans/`, and a verification that reads these folders would fail on files no task owns.
9. Progress: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs view <plan>`. It regenerates the table of PROGRESS.md from the plan (plan columns taken from the frontmatter, statuses reread from PROGRESS.md and git, cells aligned, text around kept) and creates `progress.json` if it is missing. A task merged by hand without the `pilot` command moves to "merged" there. If it exits with an error, show it and do not run: the run start would fail the same way (a status outside the 7 in PROGRESS.md, for example). If PROGRESS.md changed (`git status --porcelain -- <plan>/PROGRESS.md`), show the rows that change other than by spaces, then commit it alone on the integration branch after agreement: `progress: PROGRESS.md regenerated by progress.mjs`. Without that commit, the first scribe would carry it into its own.

## 2. The user's choices

With the question tool, ask for the mode (autonomous, stop on deviation, stop at each phase; default from the config: `default_mode`, which is `auto`, `deviation` or `phase`) and the number of simultaneous tasks (default from the config). In autonomous mode, say in one line that major issues will be settled automatically (safest option), that any human issue stops the run, and that the run also stops beyond `max_auto_decisions` auto-decisions (config, 3 by default). With `--resume`, first recall where the plan stands: `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs status <plan>`, copied as is. The rulings and the prerequisites noted done between runs were listed, offered for withdrawal and applied at point 4 of the pre-flight: nothing of them is left to list here.

## 3. Loop over the phases

For each phase, starting from the first one that has tasks neither merged nor cancelled, first place yourself at the root of the repository (`git rev-parse --show-toplevel`, then `cd` to the path returned): plan-lint, HANDOFF.md and the workflow read relative paths from there.

1. Ready: `node ${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs <plan> --phase <N> --integration <branch>` (plus `--base`). For a phase after the first, apply to the phase's prerequisites the same rules as at the pre-flight (point 7).
2. Decisions: the `decision` entries of HANDOFF.md, one line each.
3. Launch the workflow `orchestre:run-phase` (Workflow tool, parameter `name`) with `args`: `{ plan, phase, mode, parallelism, integration, base, decisions, max_fixes, escalation, max_auto_decisions, rerun, lint, agent_prefix, progress, setup, shared_setup, language }`.
   - `mode`: `auto` (autonomous), `deviation` (stop on deviation) or `phase` (stop at each phase), exactly; any other value makes the run fail. In `deviation`, a major issue that is not human no longer stops the run at once (0.21.0): no new task starts, the tasks in flight finish, then the run waits for the ruling until its deadline, `ruling_wait_minutes` of the config (15 by default, 0 to never wait). Settled in time, from the pane or by you with `rule` (see "During a run"), the ruling is applied during the run and the phase goes on. Released (`[ Decide later ]`), past its deadline or a wait that failed, the run stops as before, in `awaiting-ruling`. A human issue always stops the run at once.
   - In `phase` and `auto` modes, a task that a valid option of an open, non-human issue would amend waits for that ruling, once it is ready, at most `ruling_wait_minutes`, while the rest of the phase goes on; then it starts without it. A ruling recorded while tasks run is applied right after the next close. A held task waits once its dependencies are done and no apply runs; when that apply settled its issue, it starts without a wait.
   - `base`: `base_branch` of the config, only if it gives one.
   - `lint`: `${CLAUDE_PLUGIN_ROOT}/scripts/plan-lint.mjs`, as is; required, the workflow refuses to start without it. `progress`: `${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs`, as is; the workflow derives `worktrees.mjs` from it, in the same folder. `agent_prefix`: `orchestre:`.
   - `language`: `language` of the config, as is, `"en"` when absent. The workflow does not read the plan's own: it writes this one in the agents' prompts.
   - `setup` and `shared_setup`: copied from the config, as is; left out if it has none.
   - `max_auto_decisions`: the cap (config, 3 by default) minus the auto-decisions already taken since the start of the run or since the user's last ruling.
   - `rerun`: the tasks with the status "needs-human" that the user decided to restart, once done what was for a human; otherwise `[]`. Without it, a task that waits for a human does not start again.
4. On receiving the report, add its `auto_decisions` and its `discarded_amendments` to the run's list. `rulings_applied` lists the user's rulings that the run applied: at its start, during the run, and those the pre-flight (point 4) applied just before it. An issue settled by an apply during the run is no longer in `open_issues`: it shows in `rulings_applied`, and you do not have it settled again. A `check_skipped` of the integrator (post-merge check skipped, merged tree identical to the verified branch) is a line of the log, not an issue: it asks nothing of the user. Copy the report's `worktrees` field, if it has one: a kept worktree waits for an action of the user (commit or discard of its changes). If `progress_failures` is not empty, say it in one line per failure (`task`, `step`, `error`): a failed step only spoils the display; a failed close or apply has already stopped the run; a failed `run-end` leaves the run "in-progress" in `progress.json`, and the next run will turn it "interrupted". Then, by `status`:
   - `finished`: first the triage of the open items (`progress.mjs triage`, described in section 4). In autonomous or deviation mode, the triage asks no question: close `safe` through `ack`, say in one line per task how many items of `open` stay open, then go on to the next phase without waiting. In phase mode, offer `open` as section 4 says, then have the `open_issues` settled, then ask the end-of-phase question with the question tool. The text of the question itself starts with the summary of the phase, 5 lines at most: tasks, fixes and the reason of each rejection (field `rejections`; a rejection `by: challenge` says that the challenger changed the task's code and no verification command detected it, with the mutation in its gaps: the fix adds the missing test), deviations, findings, criteria that could not be verified (field `unverifiable`), prerequisites still open for the next phase (run plan-lint with `--phase` on the next phase to know them), reviews added (field `reviews`), tokens to read in `/workflows`. The summary never goes only into a separate message.
   - `rerun`: tasks were added to the phase, or deferred (`deferred`) because they depend on an added task. Rerun the same phase without waiting, twice in a row at most; beyond that, ask.
   - `awaiting-ruling`: have the issue `stop_issue` settled, then the `open_issues`. If it carries `circuit_breaker`, say that the cap on auto-decisions is reached and list those of the run. If it carries `inconsistency`, say that the recommended option cited tasks that nothing creates, then have it settled. If it carries `human`, say precisely what a human must do. Three stop issues come from a ruling applied during the run, all human: `Rulings not applied during the run` (apply failed: nothing of the apply is written and the rulings stay recorded, so the next run applies them), `Rulings applied during the run: output of apply not read` (apply committed, but its output could not be checked: before the next run, read the last commit `progress: rulings …` on the integration branch and the issues of `progress.json`) and `Rulings refused by apply during the run` (the same procedure as for a refusal at the run start, `rulings_refused` below: say why each was refused, and have settled again the issues apply reopened). In `deviation` mode, an issue that is released, past its deadline or whose wait failed stops the run in `awaiting-ruling` with that issue as `stop_issue`, the others still waiting in `open_issues`; an issue ruled during the run but not applied before the stop stays in `open_issues`, and the next pre-flight applies its ruling. In mode `deviation`, an issue the run waits for that the user releases with `[ Decide later ]` stops the run as when its deadline passes, because a release is not a ruling (D3). On a stop, `open_issues` can hold an issue already ruled during the run and not applied yet. Before asking the user, read `pending_rulings` in `progress.json`, do not ask again about an issue ruled there, and tell the user that the next run start applies it. A `stop_issue` already ruled from the pane (its id in `pending_rulings`) is not asked again either: its ruling is applied at the pre-flight (point 4), and its task goes in `rerun` if the ruling restarts it. A ruling on a human issue recorded during a run, even applied by an apply of that run, neither lets the run go on nor restarts its `needs-human` task: the task only starts again in `rerun`. A run that stops (stop issue or circuit breaker) starts no new wait nor apply, and first lets the waits and the apply in flight finish, up to their deadline (`ruling_wait_minutes`, 15 min by default): a wait left behind would mark its task waiting again after the run end. An amendment that a ruling applied during the run makes to a task already running is not added to it: if the task merges, its close writes the amendment as a blind-spot (`blind-spot · major · amendment not applied to <id>: …`) and lists it in `discarded_amendments`; otherwise it stays in the task file for the next run. A stop issue `Progress of <id>: output of close not read`: close ran and has already committed, but the copy of its output could not be checked; as its context says, read the commit `progress(<id>): <status>` on the integration branch and HANDOFF.md under `## <id>`, and say what close rejected or discarded there (its `needs-human` and `blind-spot` entries). Never run `progress.mjs close` again by hand: the close is written. A stop issue `Progress of <id> not committed` whose context lists `HANDOFF entries not written`: close was refused and wrote nothing; before the new run, write these entries under `## <id>` in HANDOFF.md, one `- ` line each, as given, then commit them on the integration branch, together with `<plan>/DISCOVERY.md` if `git status` shows it modified (the scribe wrote it before the refused close). A context that also lists `Automatic decisions not taken`: do not write those lines; these decisions were not applied, and their issues are back in `open_issues`, to settle as below. The issues of a task whose progress was not committed are settled by a free answer: they have no entry in `ISSUES.json`, so `rule` refuses their options. Offer their options from the workflow return all the same (`open_issues` and `stop_issue` keep their actions), then write the actions of the chosen option by hand, as for `merged_unclosed` (below), but without the decision line: its entries under `## <task>` of HANDOFF.md, its added tasks and amendments; run plan-lint until "valid plan", commit on the integration branch, then record the answer with `rule` and a text, `option <id>: <description>`, which writes the decision line at the next run start. If `rule` refuses that text after the actions of the option were committed (the issue is no longer in `progress.json`, for example), write the decision line by hand: `decision · major · <title>: option <id> settled by the user — <description>` under `## <task>` of HANDOFF.md, then run plan-lint until "valid plan" and commit, so that committed actions never stay without their decision line. A post-merge check that failed has the options `repair` (recommended) and `stop`, and its task stays merged: on `repair`, repair here, on the integration branch, until two green passes of the task's verifications, commit, then record this ruling with `rule` (below) and rerun the phase; on `stop`, go to the end. For any other issue, record the chosen options with `rule` (below), then rerun the same phase and, if the decision restarts a task that waits for a human, with its id in `rerun`; unless the user chooses to stop: go to the end then. Without `stop_issue`, the run stopped at its start on rulings that `progress.mjs apply` refused (`rulings_refused`, each with its `reason`, named in `detail`): no task started, and the other rulings are applied (`rulings_applied`). Say why each was refused. An issue is open again only when apply reopened it, the refused option invalid with its reason (plan-lint or an action refused the option, or the issue has no entry in `ISSUES.json`): have it settled again. A ruling on an unknown or already settled issue, an absent option or an option already invalid is dropped, and nothing is reopened: have the issue settled again only if it is still open in `progress.json`.
   - `partial`: for each task of `waiting` (status "needs-human"), say what a human must do, from HANDOFF.md; it will only start again in `rerun`. For each task of `waiting_on_prerequisites`, say which prerequisite of PREREQUISITES.md it waits for; it will start again on its own at the next run once that prerequisite is `done`, without going through `rerun`, unless it is also "needs-human" in PROGRESS.md: then put it in `rerun` too. If the report has `deferred` tasks or `added_tasks` of the current phase, first rerun the phase without waiting, twice in a row at most: they will start. For each blocked or failed task, give the exact reason (field `blocker` of the report, not the worker's summary) and, if there are any, the rejections of the earlier attempts (field `rejections`), then offer: fix it here on its branch, rerun the phase, or stop. Its branch: `branch` of the report (its worktree may have been removed at the end of the run: the branch stays, it is the one to fix). If `branch` is null or missing from git, take the most recent of `git branch --list "task/<id>*" --sort=-committerdate`; if there is none, for a plan migrated from orchestre 0.11, the most recent of `git branch --list "tache/<id>*" --sort=-committerdate` (`migrate.mjs` rewrites the plan's text, never the branches of git). A branch of an earlier run is first brought up to date with the integration branch (`git merge <integration branch>`, never a rebase). After a fix made here: two green passes of the verifications, then an evaluation by the agent `orchestre:evaluator` (definition of done, diff, results of the verifications, report of the fix), and only if its verdict is `pass`, a `--no-ff` merge into the integration branch with the message "task <id>: <title>" (the title without quote, backtick, dollar or backslash), status "merged" through progress (pilot's action, below), then a rerun of the phase: the remaining tasks will start on their own.
   - `error`, or a run interrupted: explain, then offer to launch a **new** run of the phase, never to resume the interrupted run. plan-lint and git history skip the tasks already merged. A `detail` that starts with "progress: run not opened": the script refused to open the run and no task started; show its error and settle it first (`progress.json` unreadable: delete it, it is rebuilt from PROGRESS.md, HANDOFF.md and git). The rulings recorded are not applied yet: the next run applies them. A `detail` that starts with "progress: rulings not applied": `progress.mjs apply` failed at the run start (main checkout not on the integration branch, commit refused by a hook) and no task started; settle its cause, the rulings stay recorded. A `detail` that starts with "progress: output of apply not read": apply ran but its output could not be checked; read its commit `progress: rulings …` on the integration branch and the issues of `progress.json` before the new run.
     A `detail` that starts with "agents not answering:": the circuit breaker tripped, after two agent calls in a row without an answer. Say to check the connection of `claude` (`/login`) and the usage limit, then offer a new run of the phase. The breaker itself leaves no issue to settle, and the branches of the tasks in `interrupted` are taken up by the next run, from their branch, except a task that is also in `merged_unclosed` with `merge: "unknown"`: its merge may have run, check it first (below).
     What the return carries besides the breaker was recorded before the trip, not by the breaker: a `stop_issue` or `open_issues` are settled as usual, with the question tool and `rule`, before the new run. "No issue to settle" only applies to the breaker.
     A non-empty `merged_unclosed`: these tasks were merged, then interrupted at their replanning or their scribe (or interrupted at their merge: `merge: "unknown"`, below), so the next run does not take them up and what their close would have written is lost. List each task with its `deviations`, `reviews`, `unverifiable` criteria and `issues`; say that the next run will not take it up because it is already merged; have every one of its `issues` settled with the question tool before the new run, as for `open_issues`: they include the issues that autonomous mode had decided automatically, whose decisions, added tasks and amendments were never written, so never present them as already applied. An empty `merged_unclosed` adds nothing. Write its deviations and reviews into HANDOFF.md after agreement. These issues reached neither `progress.json` nor `ISSUES.json`, so `rule` refuses them: they are the only issues whose decision line you write by hand. Write the chosen option yourself, as the tasks the pilot writes below: the entry `decision · major · <title>: option <id> settled by the user — <description>` under `## <task>` of HANDOFF.md, then its added tasks and amendments; run plan-lint until "valid plan", then commit on the integration branch. Every other issue goes through `rule`.
     An entry with `merge: "unknown"`: the task was interrupted at its own merge, which may have run before the integrator stopped answering. Before the new run, check whether a commit `task <id>:` is on the integration branch (`git log <integration branch> --format=%s --grep "^task <id>:"`). If it is, the task is merged: handle the entry as above, and since its post-merge check never ran, run the task's verifications on the integration branch before the new run, as for `repair` (two green passes; a failure is repaired there and committed). If it is not, the merge did not run: say that the next run takes the task up from its branch, as for the other tasks of `interrupted`, and settle or write nothing of that entry.

   Having an issue settled: question tool, one option per choice, the recommended one first, with its impact and its `effect`. An option with `valid: false` is not offered: say its `invalid_reason` in one line next to the question. An issue with no valid option, or inherited from 0.19 (`without_actions`, its options all invalid), expects a free answer. So does an issue of `progress.json` that has no entry in `ISSUES.json` (a stop issue known only from `progress.json`, which the run end recorded because the close of its task was not written), since `apply` refuses an option whose actions it does not know: its answer is always recorded as a text. When the workflow return gives its options (the issues of a task whose progress was not committed, above), offer them, write the actions of the chosen option by hand as said above, then record `rule` with the text `option <id>: <description>`; otherwise, offer no option and ask for a free answer. With at least two issues whose recommended option is valid, the first question is `Accept the N recommended options?` (N being their number, "Yes, all of them (recommended)" and "No, one by one"): on yes, record them in one `rule` as `{"items":[…]}`, and ask nothing more about them; on no, one question per issue as above. Then record the answer, between two runs, with the `progress.mjs rule` block below: `{"issue":"<id>","option":"<option id>"}`, or `{"issue":"<id>","text":"<answer>"}` for a free answer, "Other" included; several at once as `{"items":[…]}`, recorded whole or not at all. The id of an issue (`<task>-<n>`) is its `id` in the `issues` of `progress.json`. `rule` only notes the answer in `progress.json`: it is applied at the pre-flight of the next run (`progress.mjs apply`, point 4), or during a run, right after a close or before a held task starts, by the workflow. Never pass an option in `args`, and never write the decision or its actions yourself (the issues of `merged_unclosed`, and the actions of the issues of a task whose progress was not committed, aside, above). If `rule` refuses an answer (unknown or settled issue, an issue that already has a ruling recorded, option invalid, with its reason), say why; `progress.mjs unrule` withdraws a ruling recorded and not applied yet (same JSON as `rule`, `{"issue":"<id>"}`). The `open_issues` are settled before the next run, whatever the status.

   ~~~sh
   node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs rule <plan> <<'ORCHESTRE_JSON'
   {"issue":"<id>","option":"<option id>"}
   ORCHESTRE_JSON
   ~~~

   Tasks the pilot writes, between two runs and never during one: when a ruling, an evaluation on a real model or the user asks for work that no remaining task covers, first amend a task not yet started (status `todo` or `added`) that owns the files concerned, with criteria and verifications added. Otherwise apply the plan's splitting rule ("Own task only for a reason" in `${CLAUDE_PLUGIN_ROOT}/skills/prepare/format.md`): one task per module, one criterion of done per finding. When two of the tasks you would write share files, ask with the question tool "Group these <N> findings?", with "One task per module (recommended)" and "One task per finding", each option giving the number of tasks it writes. Write them on the task template of that format (a free id, `model` and `model_reason`, owned files, verification, definition of done), run plan-lint until "valid plan", then commit the task files alone on the integration branch: `plan(<n>): add <ids>`.

   Pilot's actions on progress, between two runs and never during one: PROGRESS.md is no longer edited by hand. A task merged by hand, or that the user cancels, goes through the `progress.mjs pilot` block below (`"status":"cancelled"` for a cancel), run in a single call, then a commit of PROGRESS.md alone on the integration branch: `progress(<id>): <status> by hand`. The reason goes in as it is, apostrophes included: nothing in a quoted heredoc is read by the shell (never `--json '…'` with a `\u0027`, which the Bash tool of Claude Code turns back into a quote).

   ~~~sh
   node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs pilot <plan> <<'ORCHESTRE_JSON'

   ORCHESTRE_JSON
   ~~~

## 4. End

Final summary: tasks merged, integration branch ready for a PR, major entries of HANDOFF.md, context recommendations. List apart, first, the auto-decisions (task, issue, option kept), the amendments not applied and the actions done by hand outside the evaluated loop: they are the first points to review in the PR. Then list the `review` entries of HANDOFF.md, for the user to do before the PR: the files the agents may not read or write, to review or change, and the commands they may not run. For the files, give the user the command to run themselves in a separate terminal (`git diff <base_branch>...<integration branch> -- <files>`): do not show it yourself, a secret slipped into one of these files would enter your context. Then list the `ticket` entries of HANDOFF.md, to open after the PR. When the plan is finished and reviews or auto-decisions are still open in `progress.json` (without `done` nor `ticket`), say in one line how to close them: in the `/progress` pane, the buttons of the detail card of each one (Done, Ticket, Edit text), without a turn; or `/orchestre:done <plan>`, which lists them and closes them on a one-line answer. When the plan is finished, say also that `[ Close the plan ]`, in the run card of `/progress`, makes it disappear from the display, in this session and the next ones, until a run starts on it again. Triage of the open items, at the end of the command and at the end of each phase (status `finished`): `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs triage <plan>`, which writes nothing and prints JSON `{ plan, base, integration, safe, open }`. `safe` lists what the pilot may close alone, each item `{ kind, task, text, reason, detail }` with a `reason` among `duplicate`, `superseded`, `no-diff` and `worktree-gone`. Close them in one write by passing `safe` as it is to `ack` (`{ "items": <safe> }`, in a heredoc as in `/orchestre:done`), then say in one line per `reason` what was closed. `open` lists the rest as `{ task, items: [{ kind, task, text }] }`: never close any of it. Offer `open` to the user with the question tool only in phase mode, at the end of a phase before the end-of-phase question, and at the end of the command, by group of `task` (`null` is the source plan): "Done", "Ticket", "Keep open". At the end of a phase in autonomous or deviation mode, do not offer it: say in one line per task how many of its items stay open, ask nothing, and go on to the next phase. A non-zero exit of `triage` (2: plan not found or ambiguous; 1: `progress.json` unreadable; the message is on stderr) is reported as "triage not available" with its message: close nothing alone, offer the open reviews and auto-decisions of `progress.json` to the user as before where `open` would be offered, and never read the failure as an empty `safe` list.

End with a table per task, which measures the cost and the quality of the work: attempts, rejections of the evaluations, fixes, major deviations, auto-decisions, actions done by hand; the tokens of each task can be read in `/workflows`. You never merge into `main` and you never push.

## During a run

The agents work in the main checkout. While a run is going on, you do not touch it: no `git switch`, `checkout`, `stash`, `reset` or commit, no file write, and `git status` only with `GIT_OPTIONAL_LOCKS=0`. A command that compares two commits (`git diff <a>...<b>`, `git log`) stays allowed. If the user asks for something else on the repository, tell them you will do it at the end of the run, then do it at that moment.

Settling an issue during the run (0.21.0). You may settle an open issue while the run goes on: a non-human issue that holds a task or that the run waits on (`/orchestre:status`, or `progress.mjs status <plan>`, lists them as `now`). Ask the question tool as in section 3, then record the answer with `rule` (block above), which only writes `progress.json` and so touches neither the checkout nor git; the workflow applies it itself (`apply`) and the task starts with the amendment. The only writes you may make during a run are `progress.mjs rule`, `release` (`{"issue":"<id>"}`: the tasks the issue holds start without waiting for it, the issue stays open) and `did` (`{"prerequisite":"<id>"}`: a manual action the user did; `apply` writes it into PREREQUISITES.md). They are what the buttons of the pane do; you write no file of the repository, and no other write is allowed. A human issue still stops the run at once, whatever answer was recorded. To know where the plan stands, `/orchestre:status` only reads and can run during the run; `node ${CLAUDE_PLUGIN_ROOT}/scripts/progress.mjs status <plan>` too, and also shows the step of each task in progress.

## Context

If your context approaches the cap of the config (`pilot_context_cap`, 0.65 by default), finish the current phase, then offer to go on in a new session with `/orchestre:run <plan> --resume`. The state is entirely in the plan and in git.
